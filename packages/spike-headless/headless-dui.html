Architecture proposal · DUI

Headless controllers, app-owned components

A model where the library owns behavior and your app owns the markup and styles — tested on two components, with the full source of one below.

Bottom line

Today, changing how a DUI component is shaped means changing DUI. Styles live in your app; the markup they target lives in a different repo. You can restyle from outside, but you cannot move an element, add one, or remove one.

This model moves the template into a file your app owns. Behavior — state, keyboard handling, ARIA values, popup positioning — stays a dependency, delivered as a controller that hands you bags of properties to spread onto your own markup.

It works. Both converted components render pixel-identically to the library versions and behave identically. The change that was previously impossible became three lines of cut and paste.

The problem

Customization lives far from the thing it customizes

With shadcn, “make the select denser” is an edit to select.tsx. With DUI it is an edit somewhere in your app’s CSS, expressed through an indirection layer you have to learn first — and that layer is not one thing. A single component is customized through a mix of typed properties, bare attributes, exported parts, component-scoped custom properties, and inherited design tokens, each with different rules about what wins.

One component, five ways in

MechanismExampleTypedDocumented
Propertiesvalue, placeholder, disabledYesYes
Bare attributessize="xs"No — not declared anywhere, never validatedValues only
Exported parts::part(trigger)No2 of 10
Component custom properties--select-item-padding-yNoNone, until this work
Inherited design tokens--space-2, --text-smNoSeparately
Theme bridgeapplyTheme()YesYes

None of it is consistent between components, and that is measurable rather than felt:

  • 80 of 111 registry entries document zero CSS custom properties.
  • 25 of 65 components that export parts document fewer than they export. Combobox exports seven and documents none.
  • A sweep of every custom-property declaration in the library found five that no app could reach at all — the knob existed, but it was declared on an element inside the shadow DOM where an outside value cannot win. Closing that gap required a library release. (Fixed separately; it was a four-component inconsistency, not a design flaw.)

The agent argument

The shadcn case is now usually made about agents: an AI can directly edit components/ui/button.tsx in your project, whereas with Material UI it has to work out which theme override, sx prop, or styled wrapper achieves the result without breaking other instances. Substitute DUI’s layered style model and the complaint is the same one. Given that agent-readability is an explicit DUI goal, this is the version that should sting.

The surface also resists documentation in a way that compounds. Four of select’s ten parts are computed at runtime — part="${this.#itemPart(...)}" — so an agent reading the source cannot enumerate them without executing it. What remains is maintained by hand in a registry that also generates llms.txt, which means the file agents are pointed at inherits the drift. It was already wrong for select, combobox, and twenty-three others.

More documentation is not a fix here, because the thing being documented is an accident of implementation. The class names copied styles depend on are not part of any contract; renaming one passes the type checker, passes the linter, logs nothing, and leaves an unstyled element on the page.

And when the knob does not exist

Then it is a round trip into the library, and the round trip is not small. Rolling out the size attribute across the component set took 14 commits, 31 files, 1,198 insertions — the components package, the docs registry, eight demo pages, regenerated reference material, and a coordinated change in the primitives repo, then a version bump and an npm publish.

The same capability, written in a file the app owns, was 27 lines.

Copying the styles alone does not fix it

An earlier experiment tried the obvious answer: copy the styled component into the app and keep the behavior class as a dependency. It solved appearance and nothing else. Moving one icon produced 11 compile errors, because every value the template binds is a JavaScript private field — and the workaround that shipped instead was uglier than the ::part() code it was meant to replace. The template was never in the copied file. That is what this model changes.

The idea

Split behavior from template, not styles from markup

Instead of a base element that owns a template, the library ships a headless controller that owns state and behavior and returns plain objects you spread onto your own elements. This is the Lit equivalent of Radix's asChild, React Aria's hooks, or Zag's connect().

class SelectController implements ReactiveController {
  constructor(host: ReactiveControllerHost & HTMLElement, options: SelectControllerOptions)

  // read-only state
  get isOpen(): boolean
  get options(): SelectOption[]
  get selectedOption(): SelectOption | undefined
  get displayValue(): string
  get hasValue(): boolean
  get highlightedIndex(): number

  // prop bags — each spread onto exactly one element
  get triggerProps(): SpreadProps
  get valueProps(): SpreadProps
  get popupProps(): SpreadProps
  get scrollerProps(): SpreadProps
  get listboxProps(): SpreadProps
  get itemTextProps(): SpreadProps
  itemProps(index: number): SpreadProps

  open(): void
  close(): void
}

You wire it up once, telling it how to read your component's state:

#select = new SelectController(this, {
  getOptions:  () => this.options,
  getValue:    () => this.value,
  getDisabled: () => this.disabled,
  onChange: (value, option) => {
    this.value = value;
    this.dispatchEvent(new CustomEvent("value-change", { detail: { value, option } }));
  },
});

Then you write whatever markup you want, spreading the right bag onto each element:

override render(): TemplateResult {
  const c = this.#select;

  return html`
    <div class="trigger" part="trigger" ${spread(c.triggerProps)}>
      <span class="icon">
        <dui-icon><svg viewBox="0 0 24 24" …><path d="m6 9 6 6 6-6" /></svg></dui-icon>
      </span>
      <span class="value" part="value" ${spread(c.valueProps)}>
        ${c.hasValue ? c.displayValue : this.placeholder}
      </span>
    </div>

    <div class="popup" part="popup" ${spread(c.popupProps)}>
      <dui-scroll-area ${spread(c.scrollerProps)}>
        <div class="listbox" part="listbox" ${spread(c.listboxProps)}>
          ${repeat(c.options, (o) => o.value, (o, i) => this.#renderItem(o, i))}
        </div>
      </dui-scroll-area>
    </div>
  `;
}

Nothing in the controller knows what those elements are called, what classes they carry, or what order they appear in.

Ergonomics

What it feels like to change something

Three changes were made to the owned file, as an app developer would make them.

ChangeCostPrevious model
Add a denser size="compact"20 lines of CSSAlso possible — this was never the hard case
Move the chevron before the label3 lines moved, 3 padding linesImpossible
Add a count badge to the trigger34 linesImpossible — needs new markup

The second one is the whole argument. Here is the same change under both models:

  background-color: currentColor;

<!-- AFTER: the headless model. You move the element. -->
-      <span class="value" part="value" ${spread(c.valueProps)}>…</span>
       <span class="icon">…</span>
+      <span class="value" part="value" ${spread(c.valueProps)}>…</span>

The old version hides the library's <svg> and paints a replacement over it with a masked data URI, because the real element is unreachable. The new version moves the element.

Using it

How a developer installs and works with this

Two routes, and the important thing is that the first one does not change. You install the package and import a component exactly as you do today. Owning a file is opt-in, per component, at the moment you need it.

// 1. Ready-made. Unchanged from today - import and use.
import "@dui/components/select";

<dui-select .options=${fruits} value="apple"></dui-select>


// 2. Owned. The file lives in your repo; you edit it.
//    Today: copy it in. Later: `dui add select`.
import "./components/dui/select.ts";

<dui-select .options=${fruits} value="apple" size="compact"></dui-select>

You reach for route 2 when you hit something the default cannot do — a density that does not exist, an element in the wrong place, a badge that was never anticipated. Everything else stays a normal dependency, so a project can own two components and import thirty-eight.

  • You own the component file — markup, styles, and the wiring between them. Controllers, design tokens, leaf elements like <dui-icon>, and the shared spread directive all stay ordinary dependencies.
  • Behavior fixes still arrive automatically; style improvements to a file you own do not. Same bargain shadcn makes.
  • A dui add select command is the small part. The file it would emit already exists in the library in the right shape, so there is no transformation to write — it copies, and records the source version and a style hash in the header so a later dui diff can offer upstream changes as a patch instead of reporting your edits as deletions.
  • Tag names are the open question. Custom element names are global, so an owned select.ts and the library’s cannot both be <dui-select>. Neither answer is free, and it needs settling before a CLI exists.
Trade-offs

What this costs

CostDetail
Your app owns ARIA correctness14 attributes now depend on spreading the right bag onto the right element. Forgetting popupProps costs the popup's top-layer rendering and dismissal, not just a label. A ~25-line development-mode check catches most omissions; it cannot catch a bag spread on the wrong element.

This is the standard headless trade-off, not a novel risk. React Aria's hooks return triggerProps, valueProps and menuProps to spread onto your own elements; Zag.js returns getTriggerProps(), getContentProps() and getItemProps() for the same purpose. Both are widely used and carry the identical failure mode. (shadcn is a partial parity: Radix renders the elements itself, so you own composition rather than attribute application — you can break the relationships by restructuring, but you cannot forget to apply an attribute.)
The contract is enforced by name, not contentsRenaming a prop bag is a compile error at the exact line. Moving a handler between bags type-checks cleanly and silently kills the keyboard. That is a library bug for library tests, not broken app code — but it is invisible.
Every primitive must be inverted onceRoughly 40 components. The work is mechanical once the pattern is established — tabs cost meaningfully less than select did, because the second conversion reuses the first's decisions. It is still a rewrite rather than a refactor.
Compound components need registrationParts composed in your app's markup cannot be found by the controller, so each one registers itself. Two protocols were needed for tabs, and the second failed silently until the screenshots were compared.
The library's surface changes shapeProp-bag boundaries become public API you cannot casually change, and DUI still ships ready-made components alongside the controllers. Two things pull the other way. The component scope can shrink: built-in variants exist today because apps cannot add their own — if size="compact" is 20 lines in a file you own, the library need not ship four sizes for every component. The two-repo split can collapse: dui-primitives and dui-components are separate because the styled class extends the primitive class across a package boundary. Replace that inheritance with composition and the split has no technical reason to exist — removing what has been a significant source of iteration friction.
Evidence

What is proven and what is not

Proven

  • Visual fidelity. Select: 0 differing pixels across 7 closed-state pairs and both open states. Tabs: 0 differing pixels in both orientations, before and after selection.
  • Behavior stays a dependency. Keyboard navigation, focus management, popup positioning, and form association all still come from the controller and match the library exactly.
  • Compound components work. Tabs is five elements coordinated through context, and converted at exact parity.
  • Upstream renames become loud. Under the previous model, renaming an internal class passed the type checker, passed the linter, logged nothing, and left an unstyled element on screen.

Not proven

  • Components whose state outlives an element. Toast has a global queue; nobody has answered whose host owns it.
  • Components with state larger than themselves. Data-table's prop-bag surface may exceed the component.
  • That anyone has done this at scale in web components. React Aria and Zag proved the pattern in React; no web-component library has shipped it. That is the competitive opening and the execution risk in the same sentence.

export class DuiSelectH extends LitElement {
  static tagName = "dui-select-h" as const;
  static override styles = [base, styles];

  /**
   * Form association stays here rather than in the controller. `attachInternals()`
   * can only be called by the element itself, so a controller cannot own it —
   * it would have to be handed an `ElementInternals` the host already made.
   * Five lines in the owned file is cheaper than that indirection, and the owned
   * file is a real custom element, so this is its job. See FINDINGS.
   */
  static formAssociated = true;
  #internals: ElementInternals = this.attachInternals();

  override willUpdate(): void {
    this.#internals.setFormValue(this.value);
  }

  @property({ attribute: false })
  accessor options: SelectOption[] = [];

  @property({ type: String })
  accessor value = "";

  @property({ type: String })
  accessor placeholder = "Select...";

  @property({ type: Boolean, reflect: true })
  accessor disabled = false;

  @property({
    type: Boolean,
    attribute: "align-item-to-trigger",
    reflect: true,
  })
  accessor alignItemToTrigger = true;

  @property({ type: String })
  accessor name = "";

  /** Show a "position of total" badge in the trigger. */
  @property({ type: Boolean, reflect: true })
  accessor badge = false;

  #select = new SelectController(this, {
    getOptions: () => this.options,
    getValue: () => this.value,
    getPlaceholder: () => this.placeholder,
    getDisabled: () => this.disabled,
    getAlignItemToTrigger: () => this.alignItemToTrigger,
    onChange: (value, option) => {
      this.value = value;
      this.dispatchEvent(
        new CustomEvent("value-change", {
          detail: { value, option },
          bubbles: true,
          composed: true,
        }),
      );
    },
  });

  /**
   * The controller exposes `options`, `selectedOption`, `displayValue`,
   * `hasValue`, `highlightedIndex` and `isOpen` — but not `selectedIndex`, which
   * it keeps private for its own alignment maths. Recomputing it here from
   * public state is one line and needs nothing private, but the controller
   * should just expose it. See FINDINGS step 4, change 3.
   */
  get #selectedIndex(): number {
    return this.#select.options.findIndex((o) => o.value === this.value);
  }

  override render(): TemplateResult {
    const c = this.#select;

    return html`
      <div class="trigger" part="trigger" ${spread(c.triggerProps)}>
        <span class="icon">
          <dui-icon>
            <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="none"
              stroke="currentColor" stroke-width="2" stroke-linecap="round"
              stroke-linejoin="round">
              <path d="m6 9 6 6 6-6" />
            </svg>
          </dui-icon>
        </span>
        <span class="value" part="value" ${spread(c.valueProps)}>
          ${c.hasValue ? c.displayValue : this.placeholder}
        </span>
        ${this.badge && c.hasValue
          ? html`<span class="badge" part="badge">${
            this.#selectedIndex + 1
          }/${c.options.length}</span>`
          : nothing}
      </div>

      <div class="popup" part="popup" ${spread(c.popupProps)}>
        <dui-scroll-area ${spread(c.scrollerProps)}>
          <div class="listbox" part="listbox" ${spread(c.listboxProps)}>
            ${repeat(
              c.options,
              (option) => option.value,
              (option, index) => this.#renderItem(option, index),
            )}
          </div>
        </dui-scroll-area>
      </div>
    `;
  }

  #renderItem(option: SelectOption, index: number): TemplateResult {
    const c = this.#select;
    const isSelected = option.value === this.value;
    const isHighlighted = index === c.highlightedIndex;

    return html`
      <div
        class="item"
        part="${[
          "item",
          isSelected && "item-selected",
          isHighlighted && "item-highlighted",
          option.disabled && "item-disabled",
        ].filter(Boolean).join(" ")}"
        ${spread(c.itemProps(index))}
      >
        <span class="indicator" part="item-indicator">
          ${isSelected
            ? html`
              <dui-icon>
                <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24" fill="none"
                  stroke="currentColor" stroke-width="2" stroke-linecap="round"
                  stroke-linejoin="round">
                  <path d="M20 6 9 17l-5-5" />
                </svg>
              </dui-icon>
            `
            : nothing}
        </span>
        <span class="item-text" part="item-text" ${spread(
          c.itemTextProps,
        )}>${option.label}</span>
      </div>
    `;
  }
}

customElements.define(DuiSelectH.tagName, DuiSelectH);
